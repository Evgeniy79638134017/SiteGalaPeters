# REPORT TASK-074: Диагностика 504 Gcore→origin (/media/hero-bg.mp4) — 2026-06-09

**Агент:** VS Code Claude
**Статус:** Done (диагностика, без изменений)

## Краткий вывод

**Исход (а): запросы Gcore ДОХОДЯТ до нашего Nginx, origin отвечает 200 быстро и корректно —
проблема на стороне Gcore.** Edge Gcore **обрывает origin-pull на ~200–300 КБ** (в логе `200`,
но отдано лишь ~250 КБ из 9.51 МБ, соединение закрывает клиент), поэтому 9-мегабайтный файл не
докачивается на edge → пользователям отдаётся 504. Наш origin здоров: полный файл по HTTPS
отдаётся за **0.062 с** (loopback), Range поддержан, ошибок в error.log нет, фаервол/бан/лимиты
к /media не относятся. **Ничего на сервере не менялось.**

## По пунктам (только чтение)

### 1. Access-лог: доходят ли запросы Gcore к /media/hero-bg.mp4 — ДА
- Источник **`92.223.76.20`** (диапазон **92.223.0.0/16 = Gcore**) — много `GET /media/hero-bg.mp4
  HTTP/1.1` со `статусом 200`, но `$body_bytes_sent` = **163 491 / 229 027 / 245 411 / 261 795 /
  278 179 / 294 563 …** байт (полный файл = **9 513 760**). Т.е. nginx начал отдачу (200), но
  **клиент закрыл соединение после ~200–300 КБ** — и так повторно.
- Второй источник `194.114.136.10` (curl/HTTP2) тянул крупнее — `206` Range и `200` по 3–4 МБ
  (вероятно shield/родительский узел или тест).
- Сводка кодов по `media/hero-bg`: **27×200, 2×206, 1×301** — **никаких 504/499/444 на origin**.
- Показательная строка: `92.223.76.20 … GET /favicon.ico … Referer "https://cdn.gpeters.ru/media/hero-bg.mp4"`
  — значит хотя бы один раз CDN-доставка в браузер сработала (видео грузилось с cdn.gpeters.ru).
- В `access_log` стоковый combined-формат — `$request_time/$upstream_response_time` не логируются
  (для /media это и не нужно: отдача статики, upstream нет).

### 2. Error-лог: ошибок нет
- Текущий `error.log` — **0 байт**; фильтр `timeout|upstream|ssl|handshake|limit|closed|no live`
  пуст. Nginx не зафиксировал ни таймаутов, ни TLS-сбоев, ни срабатываний лимитов. Обрыв —
  инициирован клиентом (edge), это не ошибка nginx.

### 3. Как origin отвечает внешнему HTTPS-клиенту (loopback `--resolve … 127.0.0.1`)
```
plain GET: code=200 time=0.062s size=9 513 760  http=2
range GET (Range: bytes=0-1048575 + Accept-Encoding + Gcore-UA): code=206 time=0.041s size=1 048 576
HEAD: HTTP/2 200, content-type: video/mp4, content-length: 9513760, accept-ranges: bytes,
      cache-control: max-age=2592000, public, etag/last-modified присутствуют
```
→ origin отдаёт полный файл за 0.06 с, поддерживает Range, корректные заголовки. **Origin не тормозит.**

### 3b. TLS / SNI (важно для origin-pull)
- Сертификат: `CN=gpeters.ru`, **SAN: gpeters.ru, www.gpeters.ru** (нет `cdn.gpeters.ru`).
- При `SNI=cdn.gpeters.ru` origin отдаёт тот же gpeters.ru-сертификат; строгий клиент, проверяющий
  имя `cdn.gpeters.ru`, падает (`curl (60) no alternative certificate subject name matches cdn.gpeters.ru`).
- НО pull'ы возвращают 200 → **origin host у Gcore настроен как `gpeters.ru` (верно)**, TLS не виноват.
  ⚠️ Инвариант: origin host в Gcore ДОЛЖЕН оставаться `gpeters.ru` (под сертификат), НЕ `cdn.gpeters.ru`.

### 4. Фаервол / бан / лимиты — не блокируют
- `ufw`: **443 ALLOW Anywhere** (v4/v6), 80 тоже. 443 слушается nginx.
- `fail2ban`: единственный джейл **sshd** (Currently banned: 0). Подсети Gcore **не забанены**.

### 5. /media/ — это статика с диска, не прокси (гипотеза о провале в `location /` → Vercel — РЕФУТ)
```nginx
location /media/ { alias /var/www/media/; expires 30d; add_header Cache-Control "public"; }
```
- HEAD/GET по loopback отдаются с диска (etag/last-modified) — **в Vercel-прокси не уходит**.
- `limit_req` есть **только** в `location /api/` (zone `api_forms`). К `/media/` **никакие
  limit_req/limit_conn не применяются**. Rate-limit edge не режет.

## Итоговая причина

Origin (наш Nginx) **здоров и быстр**; запросы Gcore **доходят** и получают **200**. Сбой в том,
что **Gcore edge не дочитывает ответ** (рвёт соединение на ~250 КБ из 9.51 МБ), поэтому не может
закэшировать файл и отдаёт 504 наружу. Это поведение **edge→origin pull на стороне Gcore** —
вероятные причины: слишком короткий origin read/connect-timeout у CDN-ресурса для пути
edge→Москва, настройки сегментации/«origin shielding», либо низкая пропускная способность на
этом плече. На нашей стороне править нечего (всё здорово).

## Следующий шаг (рекомендация, отдельной задачей)

Путь B — на стороне Gcore, по убыванию надёжности:
1. **Убрать origin-pull для тяжёлого файла:** залить `hero-bg.mp4` в **Gcore Storage** (push),
   чтобы edge не тянул 9.5 МБ из Москвы. Самый устойчивый вариант.
2. **Настройки Gcore-ресурса:** поднять origin connect/read timeout; включить **origin shielding**
   с щит-POP рядом с Москвой; проверить max-object/сегментацию; origin host = `gpeters.ru`, HTTPS.
3. **Облегчить ассет:** более короткий/сжатый клип или HLS-сегменты (edge тянет мелкие сегменты
   надёжнее одного 9.5 МБ объекта по медленному pull).
4. До решения — пользователи не страдают: TASK-073 уже отдаёт постер на mobile/slow, а десктоп
   играет видео с **здорового** origin `/media/`. CDN — опциональное ускорение; `/media` остаётся
   фоллбеком (как в плане). Регресса нет.
