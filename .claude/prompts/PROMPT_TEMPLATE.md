# Шаблон промта для VS Code Claude (6-компонентная формула)

Любой промт от Cowork для VS Code Claude должен содержать 6 компонентов. Эталон надёжности: монолитный промт ≈ `P(0.8^20) ≈ 1%`, атомарный по 6 компонентам — `95%+`.

---

## 1. Контекст
- Что за проект, текущая фаза, какой спринт.
- Какие файлы релевантны (точные пути).
- Что уже сделано — фактическое состояние, не намерения.
- Что прочитать перед началом (`CLAUDE.md`, `SPRINT.md`, `ARCHITECTURE.md`).

## 2. Цель
- Один атомарный результат. Не два, не три. Один.
- Формулировка через действие (создать / переписать / починить / измерить).
- Что считается «готово» — формальный критерий, по которому можно зачекать.

## 3. Вайб
- Стилистика подхода: «дисциплинированный refactor», «защитный перфекционизм», «минимальное вмешательство», «exploratory bench».
- Чего избегать тонально: «не творчество», «не переписывай чужой стиль», «не оптимизируй преждевременно».

## 4. Технические параметры
- Кодировка, форматирование, версии библиотек.
- Команды сборки / линта / тестов (с указанием cwd, если не корень репо).
- Где живут секреты, как их читать.
- Edge cases (что считать ошибкой, что — допустимым отклонением).

## 5. Visual Guidance
- Образец-паттерн: ссылка на похожий участок кода в репо («сделай как X в файле Y»).
- При UI-задачах — скриншот / мокап обязателен.
- Структуры данных, схемы файлов — диаграмма или ASCII.

## 6. Ожидания качества
- Что попадёт в gate-условия (сборка, линт, типы, размер бандла, доступ к БД).
- Что писать в CHANGELOG.
- Какой статус выставить в SPRINT.md.
- DO / DON'T-блок: явные правила.

---

## Минимальный пример

```
# PROMPT_NNN_<краткое_имя>

## Контекст
Спринт N, задача TASK-NNN. <одна фраза, что нужно>.
Прочитай: CLAUDE.md, .claude/tasks/SPRINT.md, <файл-образец>.

## Цель
<Создать/починить ...>. Готово = <формальный измеримый критерий>.

## Вайб
Минимальное вмешательство. Используй существующий стиль из <образец>.
Никаких новых библиотек без согласования.

## Технические параметры
- <правила структуры модулей>
- <точка входа клиента БД/API>
- <валидация / edge cases>
- Команда сборки: <...>, линт: <...>

## Visual Guidance
- Layout/паттерн как в <файл-образец>
- <скриншот при UI-задаче>

## Ожидания качества
- Сборка и линт зелёные
- Дельта размера зафиксирована в CHANGELOG
- <проверка доступа к БД, если тронута>
- Статус TASK-NNN → [x]
- DON'T: <чего не трогать>
```

---

## Антипаттерны (что НЕ писать)
1. Оценка времени («это займёт 2 часа»).
2. Маркировка приоритета («КРИТИЧНО», «срочно»).
3. Pep-talk («у тебя получится», «это важная задача»).
4. Маркетинг в духе «эталонный pipeline для X».
5. Дублирование того, что уже в `CLAUDE.md`.
6. Эмодзи в промте.
7. Поле «время работы» в шаблоне `CHANGELOG`.

## Обязательные компоненты, которые часто пропускаются
1. Vibe (тон подхода).
2. Visual Guidance (образец-паттерн в репо).
3. Скриншот при UI-задачах.
4. Edge cases (что считать ошибкой).
5. DO/DON'T-блок в конце.
